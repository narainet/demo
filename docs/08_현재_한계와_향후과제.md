# 08. 현재 버전의 한계와 향후 과제

이 문서는 **이 버전이 무엇을 못 하는지**를 솔직하게 적은 것입니다.
운영 계획을 세우거나 개선 과제를 잡을 때 기준으로 쓰십시오.

기재된 수치는 2026-08-06 / 08-07 에 **실제로 돌려서 측정**한 값입니다. 추정이 아닙니다.

## 1. 실행 환경 — WAS

### 1.1 결론

| WAS | Servlet | 결과 | 필요한 작업 |
|---|---|---|---|
| **Tomcat 9.0.x** | 4.0 | ✅ **정본** | 없음 |
| **Tomcat 10.0.x** | 5.0 | ✅ 동작 | 배포 시 `migrate.bat` 1회 (소스 무수정) |
| Tomcat 10.1.x | 6.0 | ⚪ 미실측 | 11 이 되므로 문제없을 것으로 보나 확인하지 않았습니다 |
| **Tomcat 11.0.x** | 6.1 | ✅ **동작** | 배포 시 `migrate.bat` 1회 (소스 무수정) |

**이 패키지의 기준은 Tomcat 9 입니다.** 그대로 배포하면 됩니다.
Tomcat 11 이 필요하면 **배포 시 변환 1회**만 하면 됩니다 — 소스는 손대지 않습니다.
절차는 [02_설치_가이드.md](02_설치_가이드.md) §5.3 에 있습니다.

### 1.2 예전 제약과, 그것을 어떻게 풀었나 (2026-08-07)

**2026-08-06 시점까지는 Tomcat 10.1 이상에서 동작하지 않았습니다.** 원인은 화면 레이아웃을
입히던 **SiteMesh 2.4.2** 였습니다. SiteMesh 는 이렇게 동작합니다.

```
① 페이지 JSP 의 출력을 버퍼에 담는다
② 버퍼에서 title / head / body 를 뽑는다
③ 데코레이터 JSP 로 dispatch 해서 합친다   ← Servlet 6.0 부터 여기서 실패
```

③ 시점에 응답이 이미 커밋돼 있어 `forward` 가 거부됐습니다(HTTP 200 + 본문 0바이트).
SiteMesh 버전 교체·설정 변경으로는 풀리지 않았습니다 — 아래가 당시 실측입니다.

| 시도 | 결과 |
|---|---|
| SiteMesh 2.4.2 | ❌ 200 + 0바이트 |
| SiteMesh 3.1.0 | ❌ 500 — *응답이 이미 커밋된 후에는 forward할 수 없습니다* |
| SiteMesh 3.2.3 (jakarta 네이티브) | ❌ 200 + 0바이트 |
| SiteMesh 3.3.0-M3 | ❌ 200 + 0바이트 |
| SiteMesh 3.3.0-M3 + `dispatch-mode=INCLUDE` | ❌ 예외는 사라졌으나 여전히 0바이트 |

게다가 SiteMesh 2.4.2 는 **2007년이 마지막 릴리스**로 jakarta 판이 나올 전망이 없었습니다.

**→ 2026-08-07, SiteMesh 를 걷어내고 레이아웃을 JSP 태그파일로 옮겼습니다.**
버퍼링도 dispatch 도 하지 않으므로 Servlet 6.x 의 실패 모드가 성립하지 않습니다.

### 1.3 지금의 레이아웃 구조

화면 JSP 가 **자기 셸을 태그로 감싸는** 방식입니다. 응답을 가로채는 필터가 없습니다.

| 파일 | 역할 |
|---|---|
| `WEB-INF/tags/layout.tag` | 디스패처. 모든 화면이 `<lay:layout>` 하나로 감싸집니다 |
| `WEB-INF/tags/shell/{mgr,front,plain,popup}.tag` | 셸 4종 (옛 데코레이터와 마크업 동일) |
| `WEB-INF/layouts.xml` | URL → 셸 매핑 (옛 `decorators.xml` 의 패턴 목록 그대로) |
| `egovframework.com.cmm.util.EgovLayoutResolver` | 매핑 해석. 정확일치 > 최장 와일드카드 > 기본값 |

화면 JSP 는 이렇게 생겼습니다.

```jsp
<%@ taglib prefix="lay" tagdir="/WEB-INF/tags" %>
<c:set var="pageTitle">규정 목록</c:set>
<c:set var="pageHead">
  <link rel="stylesheet" href="..."/>     <%-- 이 페이지 전용 head 자원 --%>
</c:set>
<lay:layout title="${pageTitle}" head="${pageHead}">
  ...본문...
</lay:layout>
```

**레이아웃 선택은 URL 기준을 유지했습니다**(페이지에 셸 이름을 박아 넣지 않았습니다).
같은 JSP 가 URL 에 따라 다른 셸로 떠야 하기 때문입니다 — 예를 들어 게시판 상세 JSP 는
`/cop/bbs/user/*` 로 들어오면 사용자 셸, `/cop/bbs/*` 로 들어오면 관리자 셸입니다.

전역 레이아웃을 바꾸려면 여전히 **셸 파일 1개**만 고치면 됩니다.

### 1.4 검증 결과 (2026-08-07 실측)

| 제품 | Tomcat 9 + JDK 8 | Tomcat 11.0.24 + JDK 17 |
|---|---|---|
| RLMS | 스모크 32/32 · 레이아웃 75/75 | **스모크 32/32 · 레이아웃 75/75** |
| RegNex | 레이아웃 34/34 | **레이아웃 26/26** |
| LexPortal | 레이아웃 16/16 | **레이아웃 23/23** |

- 로그인 화면 응답 크기가 두 WAS 에서 **바이트 단위로 동일**합니다(렌더 결과가 같습니다).
- Tomcat 11 기동·운영 중 **SEVERE 0건**, 신규 오류 0건.
- `migrate.bat` 변환은 **32~40초, 파일 수 손실 0**.

레이아웃 회귀는 `tools/layoutcheck.ps1` 로 상시 점검할 수 있습니다
([06_도구_사용설명서.md](06_도구_사용설명서.md) 참고).

> ⚠️ 위 검증은 HTTP 응답 기준입니다. 파일 업/다운로드, CKEditor 등 **브라우저 상호작용이
> 있는 화면은 실제 브라우저로 한 번 더 확인**하시길 권합니다.

## 2. JDK — 소스 문법만 Java 8 이고, JDK 자체는 자유입니다

흔히 오해하는 부분이라 명확히 적습니다.

| 구분 | 제약 |
|---|---|
| **소스 문법** | **Java 8 고정** (`<source>1.8</source>`). `var`·record·텍스트블록 사용 불가 |
| **빌드용 JDK** | **8 / 17 / 21 모두 가능** — 실측 `mvn -o clean compile` 3종 전부 EXIT=0 |
| **구동용 JDK** | 8 확인 · 17 확인 (Tomcat 10.0 기준) |

JDK 17/21 로 빌드하면 `bootstrap class path not set in conjunction with -source 8`
경고가 뜨지만 산출물은 동일합니다.

> 소스 문법을 Java 9+ 로 올리려면 Spring 6 / 표준프레임워크의 jakarta 기반 버전으로
> 가야 하며, 그건 §5.3 의 전면 마이그레이션 과제입니다.

## 3. 데이터베이스

### 3.1 참조무결성을 DB 가 지켜주지 않습니다 ★

- **FK 제약이 26건뿐**입니다. 레거시에서 이관된 `TB_*` 테이블에는 FK 가 없습니다.
- `TB_*` 테이블에는 **PK 제약도 없습니다**(`TB_READ_DUTY` 만 UNIQUE 인덱스 보유).
  논리 키는 애플리케이션이 보장합니다.

**삭제·이동 로직을 만들 때 DB 가 막아줄 것이라 기대하면 안 됩니다.** 서비스 계층에서
연쇄 처리를 직접 확인해야 합니다. 규정 삭제 체인만 DB 트리거 7종이 담당합니다.

### 3.2 DBMS별 기능 차이

| 기능 | Oracle | MariaDB | PostgreSQL |
|---|---|---|---|
| 전문검색 | Oracle Text (한글 lexer) | 부분일치 | 부분일치 |
| 물리 `DUAL` | 있음 | 문법 지원 | **호환 테이블 필수** |

- PostgreSQL 은 `10_tables.sql` 끝의 `DUAL` 생성 블록을 지우면 **로그인 후 전 화면 403** 이 됩니다.
- MariaDB 는 적재 세션에 `PIPES_AS_CONCAT,NO_BACKSLASH_ESCAPES` 를 빠뜨리면
  오류 없이 **데이터가 조용히 훼손**됩니다.

### 3.3 RLMS 통합본의 MariaDB/PostgreSQL 시드는 라이브 검증 전입니다

- DDL 은 라이브 적재 + 스모크 검증을 마쳤습니다.
- **시드(20~26)는 Oracle 정본에서 자동 변환한 생성물**이며, 같은 생성기로 만든
  RegNex·LexPortal 세트는 검증됐지만 RLMS 통합본 시드는 아직입니다.
- 최초 설치 시 각 파일의 오류 유무를 확인하고, `30_fks.sql` 이 통과하면 참조 정합은 확인된 것입니다.

### 3.4 날짜가 문자열입니다

레거시 관행으로 대부분의 날짜·시각이 `VARCHAR2` 입니다(`YYYYMMDD` / `YYYYMMDDHH24MISS`).
DB 차원의 날짜 연산·검증이 되지 않습니다.

## 4. 애플리케이션 구조

### 4.1 오류 화면이 HTTP 200 으로 위장합니다 ★

전역 예외 처리기가 예외를 잡아 "시스템 에러" 화면을 **200 으로** 돌려줍니다.
모니터링이나 자동 점검을 붙일 때 **상태 코드만으로 성공을 판정하면 안 됩니다.**
동봉된 `tools/smoke.ps1` 은 본문의 한글 오류 문구까지 검사합니다.

### 4.2 URL 접근제어가 DB 3개 표에 분산돼 있습니다

새 화면을 만들면 `COMTNPROGRMLIST` → `COMTNMENUINFO` → `COMTNMENUCREATDTLS`
3곳에 등록하고 **재기동**해야 열립니다. 등록을 빠뜨리면 403 입니다.
점검 도구: `tools/authcheck.ps1`

### 4.3 채번 누락 = 그 기능의 첫 저장 실패

시퀀스를 쓰지 않고 `COMTECOPSEQ` + `EgovIdGnrService` 로 채번합니다.
새 테이블을 만들면 채번 행과 idgn 빈을 함께 추가해야 합니다.

### 4.4 매퍼를 3벌 수작업으로 동기화합니다

`*_SQL_oracle.xml` / `_maria.xml` / `_postgres.xml` 세 벌을 항상 함께 고쳐야 합니다.
한 벌만 고치면 다른 DBMS 에서 **조용히** 깨집니다. 자동 동기화 장치는 없습니다.
(`tools/multidb/SqlLint*` 로 검사는 가능)

### 4.5 죽은 표준 모듈

전자정부 표준 공통컴포넌트 중 쓰지 않는 화면이 일부 남아 있습니다
(휴일관리·블로그보드·바로가기·프로그램변경요청·비밀번호찾기·가입약관).
테이블을 생성하지 않으므로 **URL 을 직접 입력하면 에러**가 납니다.
메뉴에 없어서 정상 동선으로는 도달하지 않습니다.

### 4.6 화면 계층이 JSP 기반입니다

JSP 200개 / 45,029줄, JSTL 제어·출력 태그 3,825개, Spring 폼·메시지 태그 2,396개.
그중 **132개(25,059줄)가 전자정부 표준 공통컴포넌트 원형**입니다.
화면 기술을 바꾸면 이 132개를 고쳐야 하고, 그 순간 표준프레임워크 업그레이드
경로에서 갈라집니다.

## 5. 향후 과제 — 선택지와 실측 비용

### 5.1 (완료) Tomcat 10.1 / 11 대응 — 2026-08-07

**끝난 과제입니다.** 이전 판에서 "향후 과제"로 잡았던 항목이며, 실제로 적용해 이 패키지에
반영했습니다. 배경과 결과는 §1 을 보십시오. 여기서는 **실제로 든 비용**만 기록합니다.

| 항목 | 수량 |
|---|---|
| `<lay:layout>` 로 감싼 JSP | RLMS 190 · RegNex 162 · LexPortal 154 |
| 감싸지 않은 JSP(조각·include 전용·자체완결) | 제품당 12~13 |
| 손으로 손본 JSP | **5개**(본문 인라인 스크립틀릿을 `<c:set>` 으로 승격) |
| 신규 파일 | 셸 4 + 디스패처 1 + `layouts.xml` + 리졸버 1클래스 (제품당) |
| 삭제 | `decorators.xml`, `decorators/*.jsp` 5개, `opensymphony:sitemesh` 의존성 |

**우려했던 것들이 어떻게 해결됐는지**(이전 판의 "함께 잃는 것"에 대한 답):

1. ~~같은 JSP 를 URL 에 따라 다른 레이아웃으로 못 띄운다~~ →
   **레이아웃 선택을 URL 매핑(`layouts.xml`)으로 유지**해 그대로 동작합니다.
   페이지에 셸 이름을 박지 않았기 때문입니다.
2. ~~표준 공통컴포넌트 132개를 직접 수정~~ → 수정은 하지만 **기계적 3줄 치환**입니다
   (`<html><head>` 제거 → `<c:set>` + `<lay:layout>` 래핑). 본문은 손대지 않았습니다.
3. ~~`<head>` 자원이 `<body>` 로 밀려 깜빡인다~~ → **`head` 속성으로 셸에 전달**합니다.
   `<head>` 안에 그대로 들어가므로 구조가 어긋나지 않습니다.
4. ~~예외 시 `</body></html>` 없는 응답~~ → 태그파일은 본문이 예외로 끊겨도
   태그가 닫히며 셸 뒷부분이 출력됩니다.

**대신 새로 생긴 제약**

- 태그 본문은 `body-content="scriptless"` — `<lay:layout>` 안에서 `<% %>` / `<%= %>` 를
  쓸 수 없습니다. 필요하면 여는 태그 **앞**에서 값을 만들어 EL 로 참조하십시오.
- `.jspf` 조각에 `<%@ page %>` 지시부를 넣으면, 그 조각을 셸(태그파일)이 include 할 때
  번역이 깨집니다. 인코딩은 `web.xml` 의 `<jsp-config>` 로 선언하십시오(LexPortal 적용 예 참고).
- 새 실패 모드는 **래핑 누락**(셸 없이 맨몸으로 뜸)과 **이중 래핑**입니다.
  `tools/layoutcheck.ps1` 이 이 둘을 잡습니다 — 화면을 추가하면 돌려 보십시오.

### 5.2 프레임워크 전면 현대화

Spring 6 + JDK 17 + jakarta 기반 표준프레임워크 + 화면 기술 교체(Thymeleaf 등).
소스 문법 Java 8 제약이 풀리는 대신 **전 화면 재검증**이 필요한 별도 과제입니다.

참고로 Thymeleaf 3.1 은 서블릿 네임스페이스 중립이라(POM 에 jakarta·javax 양쪽 존재)
Spring 5.3 에서도 쓸 수 있습니다. 다만 JSP 200개를 템플릿으로 다시 쓰는 작업이고,
`<ui:pagination>`·`<validator:javascript>` 같은 표준 커스텀 태그는 대응물이 없어
자체 다이얼렉트를 만들어야 합니다.

## 6. 운영 전 반드시 조치할 것

기술적 한계와 별개로, **인계 직후 반드시 해야 하는 작업**입니다.

| # | 항목 | 위치 |
|---|---|---|
| 1 | DB 접속정보(암호문) 설정 | `globals.properties` — 현재 `__ENCRYPTED_VALUE_REQUIRED__` |
| 2 | 암호화 키 교체 | `context-crypto.xml` 의 `algorithmKey` + `algorithmKeyHash` |
| 3 | 시드 계정 4종 비밀번호 변경 | `sysmen` / `approver` / `lawmgr` / `user` |
| 4 | 주민등록번호 ARIA 키 교체 | `Globals.law.cryptoKey` + `…KeyHash` (송무 포함 제품) |
| 5 | 파일 업로드 경로 | `Globals.fileStorePath*` — 기본 `D:/upload/` |
| 6 | 커넥터 `URIEncoding="UTF-8"` | Tomcat `server.xml` — 없으면 한글 파라미터 깨짐 |

자세한 절차는 `03_데이터베이스_가이드.md` §4, `02_설치_가이드.md` §6.
